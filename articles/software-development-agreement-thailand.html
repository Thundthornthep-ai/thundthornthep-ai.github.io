คำตอบสั้น — Quick Answer / TL;DR

สรุป 3 ประเด็นทางกฎหมายสำคัญในสัญญาพัฒนาระบบซอฟต์แวร์:

  1. การจัดการทรัพย์สินทางปัญญา (IP): โปรแกรมคอมพิวเตอร์เป็นวรรณกรรมตามบทนิยามในมาตรา 4 แห่งพระราชบัญญัติลิขสิทธิ์ พ.ศ. 2537 และตามมาตรา 10 งานที่ผู้สร้างสรรค์สร้างสรรค์ขึ้นโดยการรับจ้างบุคคลอื่น ให้ผู้ว่าจ้างเป็นผู้มีลิขสิทธิ์ เว้นแต่ผู้สร้างสรรค์และผู้ว่าจ้างจะได้ตกลงกันไว้เป็นอย่างอื่น อย่างไรก็ดี Vendor มักเขียนสัญญาให้ตนเก็บลิขสิทธิ์ไว้ และเมื่อโค้ดเขียนโดยพนักงานของ Vendor มาตรา 9 ให้ลิขสิทธิ์เป็นของพนักงานผู้สร้างสรรค์หากมิได้ทำเป็นหนังสือตกลงกันไว้เป็นอย่างอื่น ผู้ว่าจ้างจึงไม่ควรพึ่งหลักทั่วไป แต่ต้องกำหนดให้ Vendor โอนลิขสิทธิ์ใน Developed IP เป็นหนังสือลงลายมือชื่อผู้โอนและผู้รับโอน โดยระบุว่าโอนตลอดอายุแห่งการคุ้มครองลิขสิทธิ์ตามมาตรา 17 แยก Background IP ซึ่งให้เพียงสิทธิใช้ และจัดการเงื่อนไขของ Open Source Libraries
  2. กลไกตรวจรับงาน (Milestone Acceptance & Deemed Acceptance): การกำหนด User Acceptance Testing (UAT) ควรแบ่งระดับความรุนแรงของข้อผิดพลาด (Severity 1 ถึง 4) และกำหนดระยะเวลาทักท้วง (Deemed Acceptance) เพื่อป้องกันโครงการหยุดชะงัก โดยตัวเลขประมาณ 15 ถึง 30 วันเป็นตัวอย่างเชิงพาณิชย์ มิใช่ระยะเวลาที่กฎหมายกำหนด และผู้ว่าจ้างควรกำหนดมิให้การตรวจรับโดยปริยายตัดสิทธิทักท้วงความชำรุดบกพร่องที่บันทึกไว้ในรายการข้อบกพร่องที่ค้างอยู่ หรือที่พบภายหลังภายในระยะเวลารับประกัน
  3. ความต่อเนื่องและการรับประกัน: การกำหนด Source Code Escrow เพื่อให้คนกลางเก็บรักษาซอร์สโค้ดกรณี Vendor ล้มละลายหรือทิ้งงาน และการกำหนดระยะเวลารับประกันความชำรุดบกพร่อง (Warranty Period) ไว้ในสัญญาให้ชัดเจน เพราะหากสัญญามิได้กำหนดไว้เป็นอย่างอื่น ประมวลกฎหมายแพ่งและพาณิชย์ (ป.พ.พ.) มาตรา 600 ให้ผู้รับจ้างรับผิดเฉพาะความชำรุดบกพร่องที่ปรากฏขึ้นภายในหนึ่งปีนับแต่วันส่งมอบ เว้นแต่ผู้รับจ้างได้ปิดบังความชำรุดบกพร่องนั้น

สถานการณ์ที่ผู้ประกอบการมักพบจริง

  1. องค์กรขนาดใหญ่ว่าจ้าง Vendor พัฒนาระบบ Core System มูลค่าหลายล้านบาท แต่เมื่อถึงวันส่งมอบ งานกลับไม่เสร็จสมบูรณ์ 100% ตามขอบเขตงาน (Scope of Work) ทว่า Vendor อ้างว่าระบบใช้งานได้แล้วและขอเบิกเงินงวดสุดท้าย ผู้ว่าจ้างที่ขาดความเข้าใจมักตกหลุมพรางจ่ายเงินไปก่อนโดยไม่มีรายงานตรวจรับที่ชัดเจน หรือที่แย่กว่านั้นคือ เมื่อระบบมีปัญหาภายหลัง กลับพบว่าตนไม่ได้รับมอบ Source Code และพิสูจน์ห่วงโซ่ลิขสิทธิ์ไม่ได้ เพราะสัญญาไม่ได้กำหนดหน้าที่ส่งมอบ Source Code ไม่มีหนังสือโอนลิขสิทธิ์ ไม่มีการฝาก Source Code (Escrow) และข้อสัญญามาตรฐานของ Vendor สงวนลิขสิทธิ์ไว้แก่ Vendor จึงไม่สามารถแก้ไขระบบเองได้ บทความนี้จะชี้ให้เห็นจุดพลิกสำคัญที่ช่วยเปลี่ยนผู้ว่าจ้างจากผู้ถูกคุมขังโดยระบบเป็นผู้ที่มีสิทธิในระบบอย่างครบถ้วน

ภูมิทัศน์สัญญาพัฒนาระบบและกฎหมายลิขสิทธิ์ไทย

ภายใต้กฎหมายไทย ส่วนที่เป็นการพัฒนาระบบจนสำเร็จเข้าลักษณะจ้างทำของตามประมวลกฎหมายแพ่งและพาณิชย์ (ป.พ.พ.) มาตรา 587 ซึ่งเน้นผลสำเร็จแห่งการที่ทำเป็นสำคัญ ส่วนบริการสนับสนุนหลังขึ้นระบบ การอนุญาตให้ใช้ Background IP และข้อตกลง Escrow ต้องพิจารณาตามข้อสัญญาและบทบัญญัติที่เกี่ยวข้องแยกต่างหาก อย่างไรก็ตาม มิติที่สำคัญกว่าคือ พระราชบัญญัติลิขสิทธิ์ พ.ศ. 2537 ซึ่งให้ความคุ้มครองโปรแกรมคอมพิวเตอร์ในฐานะวรรณกรรม (Literary Work) ตามบทนิยามในมาตรา 4 และเป็นงานอันมีลิขสิทธิ์ตามมาตรา 6 ทั้งนี้ การคุ้มครองลิขสิทธิ์ตามมาตรา 6 ไม่คลุมถึงความคิด ขั้นตอน กรรมวิธี หรือระบบ ซึ่งมีความสำคัญต่อการกำหนดขอบเขตสิ่งที่ผู้ว่าจ้างจะเป็นเจ้าของในงานซอฟต์แวร์

หัวใจสำคัญอยู่ที่มาตรา 9 และมาตรา 10 ซึ่งวางหลักต่างกัน มาตรา 10 บัญญัติว่างานที่ผู้สร้างสรรค์ได้สร้างสรรค์ขึ้นโดยการรับจ้างบุคคลอื่น ให้ผู้ว่าจ้างเป็นผู้มีลิขสิทธิ์ในงานนั้น เว้นแต่ผู้สร้างสรรค์และผู้ว่าจ้างจะได้ตกลงกันไว้เป็นอย่างอื่น ส่วนมาตรา 9 บัญญัติว่างานที่สร้างสรรค์ขึ้นในฐานะพนักงานหรือลูกจ้าง ถ้ามิได้ทำเป็นหนังสือตกลงกันไว้เป็นอย่างอื่น ให้ลิขสิทธิ์เป็นของผู้สร้างสรรค์ แต่นายจ้างมีสิทธินำงานนั้นออกเผยแพร่ต่อสาธารณชนได้ตามที่เป็นวัตถุประสงค์แห่งการจ้างแรงงาน และหากผู้ว่าจ้างเป็นหน่วยงานของรัฐ มาตรา 14 ให้หน่วยงานนั้นมีลิขสิทธิ์ในงานที่สร้างสรรค์ขึ้นโดยการจ้างหรือตามคำสั่งหรือในความควบคุมของตน เว้นแต่จะได้ตกลงกันไว้เป็นอย่างอื่นเป็นลายลักษณ์อักษร เมื่อ Vendor เป็นนิติบุคคลและโค้ดเขียนโดยพนักงานของ Vendor สิทธิของผู้ว่าจ้างจึงขึ้นอยู่กับทั้งหนังสือตกลงระหว่าง Vendor กับพนักงานตามมาตรา 9 และข้อสัญญาระหว่าง Vendor กับผู้ว่าจ้าง ซึ่งพระราชบัญญัติมิได้บัญญัติผลของกรณีนี้ไว้โดยตรง ผู้ว่าจ้างจึงต้องกำหนดให้ Vendor โอนลิขสิทธิ์ใน Developed IP เป็นหนังสือตามมาตรา 17 และรับรองว่าได้ทำหนังสือตกลงกับบุคลากรที่ร่วมพัฒนาแล้ว เพื่อให้ห่วงโซ่สิทธิครบถ้วน

ผลกระทบเชิงธุรกิจ Business Consequences

  • Vendor Lock-in: ผู้ว่าจ้างไม่ได้รับ Source Code หรือไม่มีสิทธิแก้ไข ทำให้ต้องพึ่งพา Vendor รายเดิมตลอดไป แม้บริการจะไม่ดีหรือราคาสูงขึ้น
  • Double Payment: จ่ายเงินงวดจนครบแต่ระบบใช้งานจริงไม่ได้ (System Non-performance) เพราะขาดเกณฑ์การตรวจรับที่วัดผลได้เชิงเทคนิค
  • IP Infringement Risk: การนำ Open Source Libraries มาใช้โดยไม่ได้รับอนุญาตหรือผิดเงื่อนไข License อาจทำให้ผู้ว่าจ้างถูกฟ้องร้องจากเจ้าของลิขสิทธิ์เดิมได้

การจัดการทรัพย์สินทางปัญญา: Developed IP, Background IP, และ OSS

สัญญามาตรฐานควรแยกแยะสิทธิในทรัพย์สินทางปัญญาออกเป็น 3 ส่วน:

  1. Background IP (Pre-existing IP): เครื่องมือหรือ Software Library ที่ Vendor มีอยู่ก่อนแล้ว ลิขสิทธิ์ยังเป็นของ Vendor แต่ควรให้สิทธิใช้งาน (License) แก่ผู้ว่าจ้างอย่างถาวร
  2. Developed IP (Foreground IP): งานที่เขียนขึ้นใหม่เพื่อโครงการนี้โดยเฉพาะ เช่น Business Logic เฉพาะตัว ควรกำหนดให้โอนลิขสิทธิ์ (Assign) ให้ผู้ว่าจ้างทันทีที่ชำระเงินตาม Milestone โดยทำเป็นหนังสือลงลายมือชื่อผู้โอนและผู้รับโอน และให้ Vendor รับรองว่าลิขสิทธิ์ในส่วนงานของบุคลากรทุกรายที่ร่วมพัฒนา ทั้งลูกจ้าง ผู้รับจ้างช่วง และผู้ประกอบอาชีพอิสระ เป็นของ Vendor ตามหนังสือตกลง หรือได้โอนให้ Vendor เป็นหนังสือตามมาตรา 17 แล้ว และผู้สร้างสรรค์ทุกคนได้ตกลงเป็นลายลักษณ์อักษรเรื่องการใช้สิทธิตามมาตรา 18 แล้ว เพื่อให้ห่วงโซ่สิทธิครบถ้วน
  3. Third-Party & Open Source Software (OSS): Vendor ควรรับรองว่าได้ปฏิบัติตามเงื่อนไข License ของ OSS ทั้งหมด และไม่ทำให้ระบบของผู้ว่าจ้างกลายเป็น Open Source โดยไม่ตั้งใจ (Copyleft effect)

การโอนลิขสิทธิ์ใน Developed IP ต้องเป็นไปตามมาตรา 17 แห่งพระราชบัญญัติลิขสิทธิ์ พ.ศ. 2537 ซึ่งกำหนดว่าการโอนลิขสิทธิ์ที่มิใช่ทางมรดกต้องทำเป็นหนังสือลงลายมือชื่อผู้โอนและผู้รับโอน และถ้ามิได้กำหนดระยะเวลาไว้ในสัญญาโอน ให้ถือว่าเป็นการโอนมีกำหนดระยะเวลาสิบปี ข้อสัญญาโอนจึงควรระบุว่าโอนตลอดอายุแห่งการคุ้มครองลิขสิทธิ์ นอกจากนี้ มาตรา 18 ให้ผู้สร้างสรรค์มีสิทธิแสดงว่าตนเป็นผู้สร้างสรรค์ และมีสิทธิห้ามมิให้ผู้รับโอนหรือบุคคลอื่นใดบิดเบือน ตัดทอน ดัดแปลง หรือกระทำโดยประการอื่นใดแก่งานนั้นจนเกิดความเสียหายต่อชื่อเสียงหรือเกียรติคุณของผู้สร้างสรรค์ เว้นแต่จะได้ตกลงกันไว้เป็นอย่างอื่นเป็นลายลักษณ์อักษร สัญญาจึงควรจัดการสิทธิทางศีลธรรมนี้ไว้ให้ชัดเจน ส่วนการลงลายมือชื่อในหนังสือโอนด้วยวิธีอิเล็กทรอนิกส์จะใช้บังคับได้เพียงใด ต้องพิจารณาตามพระราชบัญญัติว่าด้วยธุรกรรมทางอิเล็กทรอนิกส์ พ.ศ. 2544 มาตรา 9 ฉบับที่ใช้บังคับในปัจจุบัน

โครงสร้างขั้นตอนการตรวจรับงาน UAT Protocol

การตรวจรับไม่ใช่เพียงการเซ็นชื่อ แต่คือกระบวนการทางเทคนิคที่ต้องระบุ Severity Level Classification:

  • Severity 1 (Critical): ระบบล่ม ใช้งานหลักไม่ได้ — ต้องแก้ทันที ห้ามตรวจรับ
  • Severity 2 (High): ฟังก์ชันหลักผิดพลาดแต่มีทางเลี่ยง (Workaround) — ต้องแก้ก่อนขึ้นระบบ
  • Severity 3 (Medium): ทำงานผิดพลาดเล็กน้อย ไม่กระทบธุรกิจ — ตรวจรับได้แต่ต้องแก้ในระยะเวลาที่กำหนด
  • Severity 4 (Low): คำผิด หรือความสวยงาม — ตรวจรับได้

Deemed Acceptance: หากผู้ว่าจ้างนิ่งเฉยไม่แจ้งผลการทดสอบภายในระยะเวลาที่กำหนด (เช่น 15 วัน ซึ่งเป็นตัวอย่างเชิงพาณิชย์ มิใช่ระยะเวลาที่กฎหมายกำหนด) ให้ถือว่างานงวดนั้นได้รับการตรวจรับโดยปริยาย เพื่อความเป็นธรรมต่อ Vendor อย่างไรก็ดี การถือว่าตรวจรับโดยปริยายอาจทำให้ผู้รับจ้างพ้นความรับผิดต่อความชำรุดบกพร่องที่พึงพบได้ในขณะรับมอบตามประมวลกฎหมายแพ่งและพาณิชย์ มาตรา 598 ทั้งนี้ ข้อยกเว้นในมาตรา 598 คุ้มครองผู้ว่าจ้างอยู่แล้วสำหรับความชำรุดบกพร่องที่ไม่พึงพบได้ในขณะรับมอบและความชำรุดบกพร่องที่ผู้รับจ้างปิดบังไว้ ความเสี่ยงที่ผู้ว่าจ้างควรป้องกันคือความชำรุดบกพร่องที่พึงพบได้ในขณะรับมอบ ผู้ว่าจ้างจึงควรกำหนดให้ Deemed Acceptance อยู่ภายใต้การสงวนสิทธิทักท้วงความชำรุดบกพร่องที่ยังมิได้แก้ไข โดยบันทึกรายการข้อบกพร่องที่ค้างอยู่ รวมทั้งข้อบกพร่องระดับ Severity 3 และ Severity 4 ที่ตรวจรับได้ ไว้ในรายงานตรวจรับเพื่อเป็นหลักฐานว่าผู้ว่าจ้างได้อิดเอื้อนไว้ และควรกำหนดด้วยว่าการตรวจรับโดยปริยายไม่ตัดสิทธิเรียกร้องในความชำรุดบกพร่องที่พบภายหลังภายในระยะเวลารับประกันและไม่ถือเป็นการตรวจรับงวดสุดท้าย

ข้อกำหนดการเก็บรักษาซอร์สโค้ด Source Code Escrow

เนื่องจาก Source Code คือหัวใจ แต่ Vendor มักไม่ยอมส่งมอบจนกว่าจะจบสัญญา หรือบางกรณีต้องการเก็บเป็นความลับ สัญญาควรระบุเงื่อนไข Trigger Events เพื่อปล่อย Source Code จากคนกลาง:

  • Vendor ล้มละลายหรือเข้าสู่กระบวนการฟื้นฟูกิจการ (ผลของการใช้เหตุนี้เป็นเหตุปล่อยซอร์สโค้ดต้องพิจารณาตามพระราชบัญญัติล้มละลาย พ.ศ. 2483 [ต้องยืนยันมาตรา])
  • Vendor เลิกประกอบธุรกิจด้านการพัฒนาระบบ
  • Vendor ละทิ้งการให้บริการบำรุงรักษา (Maintenance) ตามสัญญาอย่างมีนัยสำคัญ

ข้อตกลง Escrow ควรให้สิทธิอนุญาตผู้ว่าจ้างทำซ้ำและดัดแปลงซอร์สโค้ดที่ปล่อยออกมาเพื่อบำรุงรักษาระบบ ในส่วนที่ผู้ว่าจ้างมิได้เป็นเจ้าของลิขสิทธิ์ตามมาตรา 10 แห่งพระราชบัญญัติลิขสิทธิ์ พ.ศ. 2537 หรือมิได้รับโอนลิขสิทธิ์ตามมาตรา 17 เช่น Background IP ของ Vendor ที่รวมอยู่ในซอร์สโค้ด เพราะมาตรา 15 (1) ให้การทำซ้ำหรือดัดแปลงเป็นสิทธิแต่ผู้เดียวของเจ้าของลิขสิทธิ์ และมาตรา 30 ถือว่าการทำซ้ำหรือดัดแปลงโปรแกรมคอมพิวเตอร์อันมีลิขสิทธิ์โดยไม่ได้รับอนุญาตตามมาตรา 15 (5) เป็นการละเมิดลิขสิทธิ์ ส่วนซอฟต์แวร์ของบุคคลภายนอกหรือ Open Source Software ที่รวมอยู่ในซอร์สโค้ดยังเป็นลิขสิทธิ์ของผู้อื่น สิทธิของผู้ว่าจ้างในส่วนนั้นจึงเป็นไปตามเงื่อนไข License ที่เจ้าของลิขสิทธิ์อนุญาตไว้

(สิทธิในทรัพย์สินทางปัญญาทั้งปวงในส่วนงานที่พัฒนาขึ้นใหม่ให้เป็นของผู้ว่าจ้างเมื่อมีการชำระเงินตามงวดงานที่เกี่ยวข้อง และผู้รับจ้างตกลงโอนสิทธิดังกล่าวให้แก่ผู้ว่าจ้างตลอดอายุแห่งการคุ้มครองลิขสิทธิ์ โดยการโอนนี้ทำเป็นหนังสือลงลายมือชื่อผู้รับจ้างในฐานะผู้โอนและผู้ว่าจ้างในฐานะผู้รับโอน และผู้รับจ้างรับรองว่า (ก) ลิขสิทธิ์ในส่วนงานที่ลูกจ้างของผู้รับจ้าง ผู้รับจ้างช่วงและบุคลากรของผู้รับจ้างช่วง หรือผู้ประกอบอาชีพอิสระสร้างสรรค์ขึ้น เป็นของผู้รับจ้างตามหนังสือตกลง หรือได้โอนให้แก่ผู้รับจ้างตลอดอายุแห่งการคุ้มครองลิขสิทธิ์ด้วยหนังสือลงลายมือชื่อผู้โอนและผู้รับโอนแล้ว และ (ข) บุคคลธรรมดาทุกคนที่สร้างสรรค์ส่วนใดส่วนหนึ่งของงานดังกล่าวได้ตกลงเป็นลายลักษณ์อักษรว่าจะไม่ใช้สิทธิตามมาตรา 18 แห่งพระราชบัญญัติลิขสิทธิ์ พ.ศ. 2537 เพื่อห้ามมิให้ผู้ว่าจ้างหรือผู้สืบสิทธิของผู้ว่าจ้างใช้ แก้ไข หรือบำรุงรักษางานดังกล่าว)

Clause: Warranty and Bug Rectification (การรับประกัน)

The Developer warrants that for a period of 12 months following Final Acceptance, the Software shall perform in accordance with the Specifications. Any Bugs identified during this period shall be rectified by the Developer at no additional cost. (ผู้รับจ้างรับประกันว่าภายใน 12 เดือนนับจากวันตรวจรับงานงวดสุดท้าย ซอฟต์แวร์จะทำงานได้ตามรายละเอียดข้อกำหนด หากพบ Bug ภายในระยะเวลานี้ ผู้รับจ้างต้องแก้ไขโดยไม่มีค่าใช้จ่ายเพิ่มเติม)

ข้อต่อสู้ของผู้พัฒนาซอฟต์แวร์และผู้ว่าจ้างองค์กร Devil's Advocate

  • มุมมอง Vendor: มักโต้แย้งว่าการขอ Source Code ทั้งหมดรวมถึงเครื่องมือที่เป็นกรรมสิทธิ์ (Proprietary Tools) จะทำให้ Vendor เสียความสามารถในการแข่งขัน สัญญาจึงควรระบุให้ชัดว่าเครื่องมือทั่วไป (Tools) ไม่ถูกโอน แต่ให้เป็น License แทน
  • Scope Creep: ผู้ว่าจ้างมักสั่งงานเพิ่มนอกเหนือจากเอกสาร Requirement (BRD) โดยไม่ยอมจ่ายเงินเพิ่ม Vendor ควรใช้กลไก Change Request Form (CR) เพื่อบันทึกการเปลี่ยนแปลง

การคำนวณเบี้ยปรับ: ตัวอย่างข้อกำหนดเบี้ยปรับร้อยละ 0.1 ต่อวันของมูลค่างานงวดที่ล่าช้า รวมไม่เกินร้อยละ 10 ของมูลค่าสัญญา เป็นข้อเสนอเชิงพาณิชย์ของ LAS ที่คู่สัญญาตกลงกันได้ตามประมวลกฎหมายแพ่งและพาณิชย์ (ป.พ.พ.) มาตรา 379 และหากสูงเกินส่วน ศาลลดลงเป็นจำนวนพอสมควรได้ตามมาตรา 383 ประมวลกฎหมายแพ่งและพาณิชย์ไม่ได้กำหนดอัตราหรือเพดานมาตรฐาน

ผู้ว่าจ้างควรระวังว่า หากยอมรับมอบงานที่ส่งมอบล่าช้าโดยมิได้อิดเอื้อน ผู้รับจ้างไม่ต้องรับผิดเพื่อการที่ส่งมอบเนิ่นช้าตามประมวลกฎหมายแพ่งและพาณิชย์ มาตรา 597 และเมื่อยอมรับชำระหนี้แล้ว ผู้ว่าจ้างจะเรียกเอาเบี้ยปรับได้ต่อเมื่อได้บอกสงวนสิทธิไว้ในเวลารับชำระหนี้ตามมาตรา 381 ข้อสัญญาตรวจรับจึงควรสงวนสิทธิเรียกเบี้ยปรับและสิทธิตามมาตรา 596 ไว้อย่างชัดแจ้ง รวมทั้งในกรณีที่ถือว่าตรวจรับโดยปริยาย และเนื่องจากมาตรา 381 กำหนดให้บอกสงวนสิทธิในเวลารับชำระหนี้ ผู้ว่าจ้างควรบอกสงวนสิทธิเป็นหนังสือในเวลารับมอบงานที่ส่งมอบล่าช้าทุกครั้งด้วย

Checklist 10 จุดตรวจสัญญาพัฒนาซอฟต์แวร์

  • นิยาม Background IP และ Developed IP ชัดเจนหรือไม่?
  • สัญญาโอนลิขสิทธิ์ทำเป็นหนังสือ ลงลายมือชื่อผู้โอนและผู้รับโอน ระบุระยะเวลาการโอน และจัดการสิทธิทางศีลธรรมตามมาตรา 18 หรือยัง และ Vendor รับรองว่าลิขสิทธิ์ในส่วนงานของบุคลากรทุกรายที่ร่วมพัฒนาเป็นของ Vendor ตามหนังสือตกลงหรือได้โอนให้ Vendor เป็นหนังสือตามมาตรา 17 และผู้สร้างสรรค์แต่ละคนได้ตกลงเรื่องสิทธิตามมาตรา 18 เป็นลายลักษณ์อักษรแล้วหรือไม่?
  • กำหนดเกณฑ์ UAT แยกตาม Severity Level หรือไม่?
  • มีข้อกำหนด Deemed Acceptance ที่กำหนดระยะเวลาทักท้วงอย่างสมเหตุสมผล และสงวนสิทธิทักท้วงความชำรุดบกพร่องที่ค้างอยู่หรือที่พบภายหลัง เพื่อมิให้การรับมอบงานโดยมิได้อิดเอื้อนทำให้ผู้รับจ้างพ้นความรับผิดตามประมวลกฎหมายแพ่งและพาณิชย์ มาตรา 598 หรือไม่?
  • ระบุเรื่อง Source Code Escrow เงื่อนไขการ Release และสิทธิอนุญาตให้ผู้ว่าจ้างทำซ้ำและดัดแปลงซอร์สโค้ดที่ปล่อยออกมาหรือยัง?
  • ระยะเวลารับประกัน (Warranty) ครอบคลุมอย่างน้อย 1 ปีหรือไม่?
  • มีข้อตกลงรักษาความลับ (NDA) และข้อตกลงระหว่างผู้ควบคุมข้อมูลส่วนบุคคลกับผู้ประมวลผลข้อมูลส่วนบุคคลตามพระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 มาตรา 40 วรรคสาม รวมทั้งเงื่อนไขการส่งหรือโอนข้อมูลส่วนบุคคลไปยังต่างประเทศตามมาตรา 28 และมาตรา 29 หากมีการส่งหรือโอนข้อมูลดังกล่าว เช่น เมื่อส่งชุดข้อมูลทดสอบที่มีข้อมูลส่วนบุคคลให้ทีมพัฒนาหรือผู้ให้บริการที่ตั้งอยู่ต่างประเทศ หรือไม่?
  • ขั้นตอนการสั่งแก้ไขงานเพิ่ม (Change Request) ระบุไว้ชัดเจนไหม?
  • การคิดค่าปรับส่งมอบงานล่าช้า (เบี้ยปรับ) ระบุอัตราและเพดานที่คู่สัญญาตกลงกันไว้ และไม่สูงเกินส่วนจนศาลอาจลดลงตามประมวลกฎหมายแพ่งและพาณิชย์ มาตรา 383 และกำหนดขั้นตอนบอกสงวนสิทธิเรียกเบี้ยปรับไว้ในเวลารับมอบงานตามมาตรา 381 หรือไม่?
  • เงื่อนไขการบอกเลิกสัญญาและการส่งคืนข้อมูล (Exit Strategy)?

คำถามที่พบบ่อย Frequently Asked Questions

ถ้าสัญญาไม่ได้เขียนเรื่องลิขสิทธิ์ ใครเป็นเจ้าของ?
ตามมาตรา 10 แห่งพระราชบัญญัติลิขสิทธิ์ พ.ศ. 2537 หากผู้สร้างสรรค์สร้างสรรค์งานขึ้นโดยการรับจ้าง ผู้ว่าจ้างเป็นผู้มีลิขสิทธิ์ เว้นแต่ตกลงกันไว้เป็นอย่างอื่น แต่หากโค้ดเขียนโดยพนักงานของ Vendor ลิขสิทธิ์ระหว่างพนักงานกับ Vendor เป็นไปตามมาตรา 9 และพระราชบัญญัติมิได้บัญญัติผลต่อผู้ว่าจ้างในกรณีนี้ไว้โดยตรง สัญญาจึงต้องกำหนดเรื่องลิขสิทธิ์และการส่งมอบ Source Code ไว้ให้ชัดแจ้งทุกครั้ง
สามารถฟ้องให้ Vendor แก้ไข Bug ได้นานแค่ไหน?
ตามประมวลกฎหมายแพ่งและพาณิชย์ (ป.พ.พ.) มาตรา 600 ถ้าสัญญามิได้กำหนดไว้เป็นอย่างอื่น ผู้รับจ้างต้องรับผิดเฉพาะความชำรุดบกพร่องที่ปรากฏขึ้นภายในหนึ่งปีนับแต่วันส่งมอบ เว้นแต่ผู้รับจ้างได้ปิดบังความชำรุดบกพร่องนั้น และตามมาตรา 601 ผู้ว่าจ้างต้องฟ้องผู้รับจ้างภายในหนึ่งปีนับแต่วันที่ความชำรุดบกพร่องปรากฏขึ้น หากต้องการให้ผู้รับจ้างรับผิดต่อความชำรุดบกพร่องที่ปรากฏหลังจากหนึ่งปีนับแต่วันส่งมอบ ต้องกำหนดระยะเวลารับประกันที่ยาวกว่านั้นไว้ในสัญญา
