# แผนทบทวนบทความและปรับธีมเพื่อการเรียนการสอน

จัดทำ 28 กันยายน 2569 — สถานะ: แผนปฏิบัติงานและทะเบียนตรวจ ยังไม่ใช่ผลรับรองเนื้อหาหรือการเผยแพร่

## เป้าหมายและขอบเขต

คงหน้า Link Page ที่ `/knowledge` และการ์ดเดิมทั้งหมด เพิ่มทางเข้าคลังการเรียนรู้เพียงหนึ่งการ์ดด้านล่างก่อน Footer คลังปลายทางรวบรวมบทความและสื่อเพื่อสอนนิสิต นักศึกษา นักกฎหมาย และฝึกอบรมในองค์กร ส่วนภายในบทความให้ปรับธีมโดยรักษาเนื้อหา ลำดับหัวข้อ ตาราง เชิงอรรถ และลิงก์เดิม เว้นแต่ตรวจพบข้อผิดพลาดและมีหลักฐานรองรับการแก้ไข

ทะเบียนปัจจุบันครอบคลุมบทความ 91 กลุ่มเส้นทาง รวม 141 ฉบับ และสื่อเดิม 18 รายการ รวม HTML 159 ฉบับ เมื่อเพิ่ม PDF ของ BTU อีก 1 รายการ คลังมี 110 รายการและเอกสาร 160 ฉบับ กลุ่มเส้นทางไม่ใช่การรับรองว่าฉบับไทยและอังกฤษมีความหมายตรงกัน

การสำรวจธีมด้วยสคริปต์พบ `wiki-wrapper` 61 ฉบับ และรูปแบบอื่น 98 ฉบับ มีชุด embedded CSS ที่แฮชต่างกัน 73 ชุด ตัวเลขนี้ใช้จัดกลุ่มงานเท่านั้น ไม่ได้หมายความว่ามีดีไซน์ที่ต่างกันจริง 73 แบบ การตรวจครอบคลุม HTML ตามทะเบียน ไม่ใช่หน้า runtime ที่ต้องเข้าสู่ระบบทั้งหมด

## 1. ยืนยันต้นฉบับก่อนตรวจ

1. จับคู่ URL ที่ผู้ใช้เปิดจริงกับไฟล์ต้นทาง ภาษา ชื่อหัวเรื่อง และแฮชข้อความ พร้อมบันทึกวันที่ตรวจ
2. ตรวจ 44 เส้นทางที่มีสำเนา LAS ซึ่งพบชื่อหัวเรื่องต่างกัน 33 เส้นทางทีละรายการ ชื่อที่ต่างกันยังไม่ใช่หลักฐานว่าข้อกฎหมายขัดกัน
3. เลือกฉบับที่เสิร์ฟจริงเป็นฐาน ไม่ใช้ไฟล์เก่าทับหน้าใหม่ หากยืนยันไม่ได้ให้ตั้งสถานะ HOLD
4. รวมสื่อ 19 รายการในทะเบียนความครอบคลุมด้วย แม้ไม่อยู่ในคิวบทความ 141 ฉบับ โดยตรวจข้ออ้างใน PDF จากหน้าต้นฉบับ ไม่ใช้ข้อความที่สกัดเพียงอย่างเดียว

## 2. ตรวจข้ออ้างทุกส่วน ไม่ตรวจเฉพาะเลขมาตรา

| ชั้นตรวจ | วิธี | ผลที่ต้องเก็บ |
|---|---|---|
| เอกลักษณ์แหล่ง | สคริปต์ตรวจ URL, hash, ภาษา, วันที่ และรายการซ้ำ | ฉบับที่ตรวจตรงกับฉบับที่อ่านจริง |
| ความครอบคลุม | แบ่งเป็นประเด็นและข้ออ้าง รวมตาราง คำถามท้ายบท FAQ และข้อมูล structured data | ทุกย่อหน้ามีสถานะ ไม่มีช่วงถูกข้าม |
| ตัวบทและคำพิพากษา | ค้นฐานในเครื่องก่อน ตรวจย้อนต้นฉบับทางการและฉบับแก้ไข วันที่มีผล บทเฉพาะกาล และสถานะคำวินิจฉัย | แหล่งอ้างอิงพร้อมหน้า/ย่อหน้าและแฮช |
| ความหมาย | อ่านข้ออ้างกับตัวบทและบริบทข้อยกเว้น ตรวจบุคคล หน้าที่ เงื่อนไข จำนวนเงิน ระยะเวลา ภาระพิสูจน์ ผลทางกฎหมาย และทางเลือก | PASS, FIX หรือ HOLD ต่อข้ออ้าง พร้อมเหตุผล |
| ข้อเท็จจริงอื่น | ตรวจสถิติ ความสามารถผลิตภัณฑ์ ประวัติ โครงการหรือทุนสนับสนุนจากหลักฐานเฉพาะเรื่อง | ไม่อ้างผลตรวจตัวบทเป็นการรับรองข้อเท็จจริงทั้งหมด |
| ฉบับภาษา | ใช้แหล่งกฎหมายร่วมกัน แต่เทียบความหมายของแต่ละฉบับแยกกัน | ไม่ลดหรือเพิ่มเงื่อนไขจากการแปล |
| ความพร้อมสอน | ตรวจตัวอย่าง คำถาม แบบฝึกหัด และเฉลยหลังตรวจเนื้อหา | ไม่ขยายข้อผิดพลาดเข้าสู่การฝึกอบรม |

เลขมาตรามีอยู่ในทะเบียนไม่ได้แปลว่าคำอธิบายถูกต้อง และการไม่มีเลขมาตราไม่ได้แปลว่าบทความไม่มีข้ออ้างทางกฎหมาย แหล่งในเครื่องช่วยค้นและลดงานซ้ำ แต่ต้องยืนยันความเป็นปัจจุบันและที่มาของแหล่งก่อนใช้อ้าง หากหลักฐานไม่พอให้ HOLD แทนการเดาหรือเติมข้อความจากความจำของโมเดล

ผลตรวจทั้งบทเลื่อนได้เมื่อทุกข้ออ้างได้รับการจัดการ: `unreviewed → source_verified → semantic_reviewed → teaching_ready` โดยมีสถานะ `hold` และ `superseded` แยกต่างหาก การตรวจบางย่อหน้าหรือการผ่าน citation firewall อย่างเดียวไม่ทำให้ทั้งบทความผ่าน

## 3. จัดลำดับและเลือกโมเดลตามงาน

เริ่มชุดทดลอง 10 ฉบับ: 6 ฉบับที่กระทบสิทธิหรือหน้าที่โดยตรง 2 ฉบับสำหรับเทียบไทย–อังกฤษ และ 2 ฉบับด้านวิชาชีพ/AI/ข้ออ้างผลิตภัณฑ์ รวมบทความ AI Legal Technology ที่ผู้ใช้กำลังดู จากนั้นตรวจ PDF BTU เป็นสื่อคนละชิ้น ไม่ถือว่าเป็นเนื้อหาเดียวกับบทความเพราะใช้ชื่อที่เชื่อมโยงกัน

คิวเดิมมี 24 ฉบับที่ถูกจัดความสำคัญสูงด้วยคำสำคัญ ต้องใช้คนอ่านยืนยันก่อนสรุปลำดับ และไม่ลดความสำคัญของฉบับที่ตัวกรองตรวจไม่พบคำเสี่ยง หลังปรับเทียบแล้วดำเนินการเป็นชุดไม่เกิน 5 ฉบับหรือ 20 ข้ออ้างต่อรอบ โดยลดขนาดเมื่อบริบทกฎหมายยาว ไม่ตัดข้อยกเว้นเพื่อให้พอดีโควตา

| งาน | เครื่องมือ/ระดับที่เสนอ | ข้อจำกัด |
|---|---|---|
| สแกนไฟล์ ลิงก์ สี วันที่ แฮช และรายการซ้ำ | Python/JavaScript | ไม่เรียกโมเดล |
| เสนอหมวด จัดรูป JSON และตรวจความครบช่อง | กฎก่อน; โมเดลเล็กที่อนุญาตเมื่อจำเป็น | ไม่ตัดสินข้อกฎหมายหรือแก้ตัวบท |
| ตรวจข้ออ้างกับหลักฐานที่จัดให้ | โมเดลระดับกลางที่ผ่านชุดทดลอง LAS; ผู้สมัครในเครื่องนี้คือ GPT-6 Sol | ยังไม่รับรองความแม่นยำจนกว่าจะทดสอบจริง |
| ประเด็นกำกวม ข้อยกเว้น สิทธิ หน้าที่ อายุความ หรือผลคดี | โมเดล reasoning ระดับสูง; ผู้สมัครคือ GPT-6 Astra | ต้องมีชุดหลักฐาน ไม่ให้ค้นจากความจำอย่างเดียว |
| ตรวจอิสระก่อนเลื่อนสถานะพร้อมสอน | ผู้ตรวจอีกครั้งในบริบทใหม่ และผู้เชี่ยวชาญมนุษย์สำหรับประเด็นสำคัญ/ข้อขัดแย้ง | การตรวจซ้ำด้วย AI ไม่แทนความรับผิดชอบของผู้สอน |
| สีและ CSS | สคริปต์/โมเดลเขียนโค้ดระดับกลาง พร้อม browser QA | ไม่ใช้โมเดลกฎหมายอ่านเนื้อหาซ้ำทุกครั้งที่แก้สี |

ชื่อโมเดลเป็นตัวเลือกตามรายการที่เครื่องมือใน session นี้รองรับ ไม่ใช่ผล benchmark และไม่ใช่การยืนยันราคา API หรือความพร้อมของ endpoint ภายนอก ยังไม่ได้สลับโมเดลหรือเริ่มงานโมเดลเป็นชุดในรอบนี้ ให้เลือกจากอัตราข้อผิดพลาดสำคัญ ความครบของหลักฐาน การยอม HOLD เวลา และ token ต่อข้ออ้างที่ผ่านจริง ไม่เลือกจากราคาหรือความเร็วเพียงอย่างเดียว

ชุดทดลอง 10 ฉบับต้องตรวจอิสระทั้งหมด หากเกิดข้อผิดพลาดสำคัญให้หยุดขยายชุด ปรับ prompt/source packet แล้วทดสอบใหม่ ระยะทำจริงทุกฉบับยังต้องมีการตรวจความหมายครบถ้วน ส่วนการตรวจซ้ำเพิ่มให้ครอบคลุมประเด็นสำคัญทั้งหมดและสุ่มฉบับทั่วไปอย่างน้อย 20% หากพบการรับรองผิดให้ขยายตรวจซ้ำทั้งชุด

## 4. ประหยัด Usage โดยไม่ลดความครบถ้วน

- สร้าง source packet ของกฎหมายแต่ละเรื่องครั้งเดียว แล้วใช้ร่วมกับหลายบทความ บันทึกฉบับและวันที่มีผลเสมอ
- ส่งเฉพาะข้ออ้างและบริบทที่เพียงพอ พร้อมตัวบท ข้อยกเว้น คำนิยาม และบทเฉพาะกาลที่เกี่ยวข้อง ไม่ส่ง HTML เมนู CSS และสคริปต์เข้าโมเดลกฎหมาย
- ให้แต่ละย่อหน้ามีรายการความครอบคลุม เพื่อป้องกันการลด token จนตกหล่นประเด็น
- ใช้ผลตรวจเดิมได้เมื่อแฮชข้อความ/ข้ออ้าง แฮชแหล่งทางการ วันที่ใช้กฎหมาย prompt/model/reviewer และนโยบายตรวจตรงกัน พร้อมตรวจว่าแหล่งยังไม่ถูกแทนที่ หากเปลี่ยนเฉพาะสีไม่ต้องตรวจความหมายใหม่ หากกฎหมายเปลี่ยนให้เปิดตรวจเฉพาะข้ออ้างที่พึ่งพาแหล่งนั้น
- แยก HTML hash สำหรับการส่งมอบออกจาก semantic text hash สำหรับผลตรวจ และเก็บ structured data hash แยกด้วย เพื่อไม่ให้ FAQ หรือ metadata เปลี่ยนแล้วหลุดจากการตรวจ
- บันทึก checkpoint ต่อข้ออ้าง ไม่เริ่มทั้งบทใหม่เมื่อรอบงานสะดุด ไม่เปิดหลาย agent ให้อ่านบทเดียวกันโดยไม่มีหน้าที่ต่างกัน
- วัด actual input/output tokens และเวลาในชุดทดลองก่อนประมาณทั้งคลัง พร้อมบันทึกส่วนที่ไม่ครอบคลุม โควตา Codex ที่ตรวจได้ใช้ไป 6% ของรอบ 7 วัน ณ การวางแผนครั้งนี้ เป็นข้อมูลแชร์ทั้งบัญชีและเปลี่ยนได้ ไม่ใช่งบที่กันไว้ให้งานนี้
- หากใช้ API ในอนาคต ต้องแยกงบจาก Codex/ChatGPT และตั้งเพดานก่อนเรียก API; รอบนี้ไม่สร้างค่าใช้จ่าย API เพิ่ม
- API prompt caching ช่วยด้านต้นทุน/เวลา แต่ไม่เปลี่ยนวิธีนับ rate limit จึงไม่ควรรับประกันว่าจะยืดโควตา Codex ส่วน Batch API มีเงื่อนไขต้นทุนและ rate-limit pool ของ API โดยเฉพาะ ไม่ใช่สิทธิฟรีเพิ่มในบัญชี Codex

## 5. ปรับธีมภายในบทความโดยรักษาความหมายของสี

| องค์ประกอบ | แนวทาง |
|---|---|
| พื้นหลัง | ครีม #f8f4ec |
| พื้นอ่าน/การ์ด | #fffdf8 |
| ตัวอักษรหลัก | #2c303a |
| สีแบรนด์ | ฟ้าเทา #5c728a |
| ลิงก์ข้อความ | #40536a พร้อมขีดเส้นใต้หรือสัญญาณอื่น ไม่พึ่งสีอย่างเดียว |
| สีเน้น | คอรัล #e46d58 สำหรับของตกแต่ง ไม่ใช้เป็นข้อความเล็กบนพื้นขาวโดยไม่ตรวจ contrast |
| เส้นขอบ | #ded4c4 |
| หัวข้อ/เนื้อหา | IBM Plex Sans Thai และ Noto Sans Thai พร้อม fallback |
| กล่องความเสี่ยง | คงแดง/เหลือง/เขียวตามความหมาย มีป้ายข้อความกำกับ |
| ตัวบทอ้างอิง | คงวรรค บรรทัด การเน้น และความแตกต่างระหว่างตัวบทกับคำอธิบาย |
| PDF/รูปเอกสาร | รักษาต้นฉบับ ไม่ย้อมสีเอกสารหลักฐานหรือสไลด์ที่อัปโหลด |

ใช้ stylesheet กลางพร้อม adapter ตามกลุ่ม template ห้ามแทนที่รหัสสีทั้งไฟล์แบบเหมา เพราะสีเดียวกันอาจใช้คนละหน้าที่ สำรวจ `article-theme-audit.json` ก่อนเลือก adapter และตรวจ inline/external CSS เพิ่มด้วย browser

นำร่องอย่างน้อย 3 รูปแบบ: บทความ Wiki, บทความที่มีกล่องความเสี่ยง/ตาราง และบทความอีกแบบที่ไม่มี wiki-wrapper ครอบคลุมภาษาไทย–อังกฤษ ตรวจ Desktop, 390px, การพิมพ์, contrast ข้อความทั่วไปอย่างน้อย 4.5:1 และสถานะ hover/focus พร้อมตรวจลิงก์จริง จากนั้นขยายทีละกลุ่ม โดยทุกหน้าต้องผ่านการตรวจ layout/ลิงก์และได้รับการตรวจภาพ หน้าแบบใหม่หรือตารางซับซ้อนต้องตรวจเพิ่ม

ใช้ semantic diff ยืนยันว่าการเปลี่ยนธีมไม่แก้ข้อความ URL ตัวบท หรือ structured data หากแก้กฎหมายให้แยก commit และผลตรวจ แสดงวันที่ปรับปรุงเนื้อหา วันที่ตรวจข้อกฎหมาย และวันที่ปรับธีมแยกกัน ไม่ลงวันที่ตรวจข้อกฎหมายเพียงเพราะเปลี่ยน CSS

## 6. ลำดับส่งมอบและเงื่อนไขผ่าน

1. ปิดช่องว่าง identity ของหน้าจริงและทะเบียนสื่อทั้งหมด
2. ตรวจชุดทดลองและเลือกโมเดลจากผลจริง พร้อมตัวอย่างรายงานต่อข้ออ้าง
3. ทำธีมนำร่องแยกจากการแก้กฎหมาย ให้ผู้ใช้ดูภาพและหน้าจริงใน preview
4. ขยายการตรวจตามความสำคัญและกลุ่มธีม มี ledger และ checkpoint ต่อชิ้น
5. รัน publication gates, link checks, visual/print/mobile checks และตรวจ diff ของหน้าที่ถูกป้องกัน
6. อัปเดต Second Brain พร้อมแหล่งที่มา ผลตรวจจริง ข้อจำกัด และลิงก์ PR แล้วขออนุมัติก่อน merge/deploy

คำว่าเสร็จหมายถึงทุกข้ออ้างมีหลักฐานหรือถูกแก้/ตัดตามการอนุมัติ ทุกฉบับภาษาผ่านตรวจ ไม่มี HOLD ค้างในบทที่จะรับรองพร้อมสอน และหน้าเผยแพร่ตรงกับฉบับที่ตรวจ หากทำเสร็จเพียงบางชุดให้รายงานจำนวนและขอบเขต ไม่รับรองทั้งคลัง
