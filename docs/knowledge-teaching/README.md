## เป้าหมายและขอบเขต

รวบรวมเนื้อหาที่มีอยู่ให้ค้นพบได้ครบ จัดหมวดตามประเด็นและลำดับการเรียน และทำให้ผู้สอนเห็นว่าส่วนใดผ่านการตรวจหลักฐานแล้ว เป้าหมายรอบนี้คือทะเบียน ต้นแบบ และแผนตรวจที่นำไปทำต่อได้ ไม่ใช่การรับรองว่าบทความทุกฉบับถูกต้องตามกฎหมายปัจจุบันทั้งหมด

ทะเบียน GitHub snapshot `e95fb61` ตรวจไฟล์ HTML ที่ติดตามใน Git ทั้ง 239 ไฟล์ พบ 91 เรื่องในกลุ่มบทความ และ 18 เรื่องในกลุ่มคู่มือหรือเครื่องมือประกอบ รวมฉบับภาษา 159 หน้า อีก 80 ไฟล์เป็น redirect หรือหน้าระบบ บัญชีแยกรายไฟล์อยู่ใน `catalog.json` จึงตรวจย้อนหลังได้ว่ารายการใดถูกนับหรือไม่นับ เพราะอะไร ตัวเลขนี้ยังไม่ใช่การรับรองความครบถ้วนของทุกระบบ LAS หรือบทความภายนอก

`override-audit.json` ตรวจทะเบียนสำเนาใน LAS checkout 44 เส้นทาง พบหัวเรื่องต่างจาก GitHub 33 เส้นทาง ความต่างของชื่อไม่ใช่ข้อสรุปว่าข้อกฎหมายขัดกัน ตัวอย่างที่เห็นชัดคือ `las-share-01.html`: GitHub กล่าวถึงอำนาจกรรมการ ส่วนสำเนา LAS กล่าวถึงจ้างทำของกับจ้างแรงงาน ต้องตรวจฉบับที่ runtime เสิร์ฟจริงและทำ content ID ก่อนรวมรายการ หน้า `/knowledge` พา browser ที่ไม่มี session ไป `/login` ในรอบตรวจนี้ จึงยังไม่ยืนยัน authenticated production

## โครงสร้างที่ควรใช้

แยก 4 ชั้นข้อมูล: (1) เนื้อหาต้นฉบับและฉบับภาษา (2) หมวดและรูปแบบสื่อ (3) เส้นทางเรียนและแบบฝึก (4) หลักฐานการตรวจ ผู้ใช้เปิดบทความเดิมได้ผ่านการ์ด ส่วนเนื้อหาการสอนและสถานะตรวจอยู่ในทะเบียนกลาง

หนึ่งเรื่องมี `content_id` ถาวรและหลาย `variant_id` ฉบับภาษาแต่ละฉบับมี hash ของตัวเอง การใช้ URL หรือชื่อไฟล์ตรงกันเป็นเพียงข้อเสนอจับคู่ ต้องตรวจความหมายก่อนยืนยัน จัดทะเบียน redirect เป็น alias เท่านั้น ไม่สร้างการ์ดเพิ่ม

| มิติ | วิธีใช้ |
|---|---|
| หมวดกฎหมาย | บริษัทและธรรมาภิบาล; สัญญาและหนี้; การลงทุน; แรงงาน; ข้อมูลส่วนบุคคล; อสังหาริมทรัพย์; ภาษี; ทรัพย์สินทางปัญญา; ผู้บริโภค; มหาชนและท้องถิ่น; วิชาชีพและเทคโนโลยี |
| ซีรีส์เดิม | Share, Shield, C&C, UP และ INVEST เก็บไว้ให้ผู้ใช้ที่คุ้นเคยค้นต่อได้ |
| ระดับ | พื้นฐาน → ประยุกต์ → ปฏิบัติงาน โดยผู้สอนอนุมัติระดับ ไม่อนุมานจากความยาวบทความ |
| กลุ่มผู้เรียน | นิสิตและนักศึกษา; ทนายความ; ผู้สนใจทั่วไป ปรับลำดับได้แต่ไม่ซ่อนคลังที่เหลือ |
| ทักษะ | อ่านตัวบท; แยกประเด็น; ตรวจสัญญา; จัดหลักฐาน; บริหารความเสี่ยง; วางแผนธุรกรรม |
| รูปแบบ | บทความ; คู่มือ; เครื่องมือ; แบบฝึก; กรณีสมมติ ต้องแยกกรณีสมมติออกจากคำพิพากษาจริง |
| เวลา | วันเผยแพร่; วันปรับปรุงต้นฉบับ; วันตรวจตัวบท; วันทบทวนบทความ ไม่ใช้วันหนึ่งแทนอีกวัน |

การจัดหมวดรอบแรกใช้ชื่อเรื่องและเส้นทางแบบ deterministic พร้อมสถานะ `proposed` จึงประหยัดโมเดลและตรวจย้อนกลับได้ เรื่องเดียวติดหลายหมวดได้ ยอดรวมต้องนับ content ID ไม่ใช่บวกยอดทุกหมวด

## เส้นทางเรียนและวิธีสอน

รายละเอียดลำดับบทความทั้งหมดอยู่ใน `learning-paths.json` และเปิดดูได้ในต้นแบบ

1. **เริ่มต้นอ่านกฎหมายธุรกิจ:** คู่สัญญา → บริษัท → อำนาจลงนาม → ผู้แทน → หนี้ → เวลาใช้สิทธิ → ความเป็นธรรมของข้อสัญญา
2. **จากบริษัทสู่ธุรกรรมของผู้ถือหุ้น:** จัดตั้ง → มติ → โอนหุ้น → ข้อตกลงผู้ถือหุ้น → ร่วมทุน → ตรวจสถานะ → ทางออก
3. **ฝึกอ่าน ตรวจ และร่างข้อสัญญา:** โครงสร้าง → คำนิยาม → เงื่อนไข → คำรับรอง → ความรับผิด → เยียวยา → เลิกสัญญา → เหตุเปลี่ยนแปลง → ข้อพิพาท
4. **วางระบบป้องกันความเสี่ยงองค์กร:** สัญญาจำเป็น → ความลับ → หลักประกัน → ข้อมูลส่วนบุคคล → แรงงาน → ป้องกันทุจริต → ประกันภัย
5. **ลงทุน ขยายกิจการ และวางทางออก:** นักลงทุน → โครงสร้างบริษัท → แฟรนไชส์ → ซื้อกิจการ → เงินทุน → ตลาดทุน → ข้ามพรมแดน → ทางออก

ทุกบทเรียนควรมีคำถามเปิดเรื่อง 1 ข้อ เป้าหมายการเรียน 2–3 ข้อ บทความหลัก ตัวบทที่ตรวจฉบับปัจจุบัน แบบฝึกข้อเท็จจริงสมมติ และเกณฑ์ประเมินแยกประเด็น/หลักฐาน/เหตุผล/ความไม่แน่นอน สำหรับนักศึกษาให้ scaffold และตัวอย่าง สำหรับทนายความให้เอกสารหลายชิ้น เงื่อนไขต่อรอง และข้อเท็จจริงที่ขาด

ต้นแบบมีงานฝึกท้ายเส้นทางแล้ว แต่ยังไม่สร้างเฉลยกฎหมายหรือแบบทดสอบที่อาจทำให้ความผิดเดิมถูกขยาย ควรสร้างหลังผ่าน semantic review ทีละบท คลังเรื่องอื่นยังอยู่ในหน้าค้นทั้งหมด ไม่ถูกตัดออกเพราะยังไม่อยู่ใน 5 เส้นทาง

## ตรวจข้อกฎหมายอย่างไรให้ใช้สอนได้

| ชั้นตรวจ | หลักฐานและผลลัพธ์ |
|---|---|
| ระบุตัวเนื้อหา | URL ที่เสิร์ฟจริง, repo revision, title และ body hash; แยก proxy override, redirect และฉบับภาษา |
| ตรวจการอ้าง | ดึงเลขมาตรา ชื่อกฎหมาย คำพิพากษา ข้อความคัด และแหล่งอ้างอิง เก็บตำแหน่งข้อความ ตรวจ comma list และช่วงมาตราครบทุกตัว |
| ตรวจฉบับกฎหมาย | หลักฐานทางการ วันที่มีผล ฉบับแก้ไข บทเฉพาะกาล และความเกี่ยวข้องของวันเกิดเหตุ แหล่งข้อมูลในเครื่องช่วยค้นแต่ไม่แทนหลักฐานทางการ |
| ตรวจข้อความคัด | เทียบต้นฉบับเต็มวรรคและข้อย่อย หาก OCR ไม่ชัดให้อ่าน PDF ภาพจริง พร้อม ORST ตามมาตรฐาน |
| ตรวจความหมาย | อ่านข้ออ้างพร้อมบริบท เทียบองค์ประกอบ ผู้มีหน้าที่ ข้อยกเว้น กำหนดเวลา ผลทางกฎหมาย และข้อจำกัดของคำอธิบาย |
| ตรวจคำพิพากษา | ยืนยันเลข/ปี ข้อเท็จจริง ประเด็น ผลคดี และแนวภายหลัง หากหาไม่ได้ให้ HOLD ไม่สร้างรายละเอียดเติม |
| ตรวจการสอนและภาษา | คำอธิบายไม่ข้ามข้อยกเว้น ฉบับภาษาแปลตรงความหมาย แบบฝึกไม่แฝงคำตอบผิด วันที่ด้านบนตรง metadata |

citation firewall เดิมมีประโยชน์เป็นด่านทะเบียน แต่ไม่พิสูจน์ความหมาย และมีขอบเขตที่ต้องตรวจให้ครบในการตรวจสอน: bare section อาจไม่ผูกชื่อกฎหมาย, comma list และช่วงมาตราภายในยังไม่ครบ จึงคง gate เดิมไว้และเพิ่มงานตรวจแยก ไม่ลดความเข้มของ gate เพื่อให้ผ่าน

สถานะควรเป็น `unreviewed → source_verified → semantic_reviewed → teaching_ready` โดยมีทาง `hold` และ `superseded` ทุกการเลื่อนสถานะต้องระบุ reviewer, article hash, source hash, เวลากฎหมายที่ใช้ และข้อจำกัด เมื่อเนื้อหาหรือกฎหมายเปลี่ยน ผลตรวจส่วนที่กระทบต้องหมดอายุทันที การตรวจเพียง 1 ประโยคไม่ทำให้ทั้งบทความผ่าน

## ใช้โมเดลและ Usage อย่างคุ้มค่า

| งาน | เครื่องมือที่ใช้ | ขอบเขต |
|---|---|---|
| นับไฟล์ ลิงก์ hash วันที่ dedupe และ diff | Python/JavaScript | ไม่เรียกโมเดล |
| เสนอหมวดและจัดรูปข้อมูล | กฎ deterministic ก่อน; local model ที่ผ่าน whitelist เมื่อจำเป็น | ไม่ตัดสินกฎหมาย |
| ค้นบริบทคลังเดิม | ดัชนีและ embedding ที่มีอยู่ | เป็น discovery ไม่ใช่หลักฐานรับรอง |
| อ่านข้ออ้างเทียบแหล่ง | โมเดล cloud สำหรับ legal review ที่ผ่านชุดทดสอบ LAS | ส่งเฉพาะบท/ช่วงข้อความและตัวบทที่จำเป็น พร้อมบริบทข้อยกเว้น |
| ข้อขัดแย้งหรือผลกระทบสูง | โมเดล reasoning ระดับสูงและผู้ตรวจอิสระ | อายุความ ความรับผิด การเลิกสัญญา สิทธิแรงงาน และคำพิพากษา ควรตรวจซ้ำทั้งหมด |
| งานความเสี่ยงต่ำที่ผ่านแล้ว | ทบทวนเมื่อ hash/แหล่ง/นโยบายเปลี่ยน | ใช้ cache ที่มีหลักฐาน ไม่ใช้ข้อความตอบเดิมอย่างเดียว |

ระบบรายงาน Codex ใช้ไป 4% ของรอบ 7 วัน ณ เวลาเริ่มงาน ตัวเลขแชร์ทั้งบัญชีและเปลี่ยนได้ จึงไม่ใช้รับประกันจำนวนบทความหรือต้นทุน โมเดลที่ตั้งสำหรับ session นี้คงเดิม ไม่ได้เปลี่ยนโมเดลเบื้องหลัง และรอบสร้างทะเบียนนี้ไม่ยิง batch LLM เพิ่ม

สำหรับรอบถัดไปให้เลือกโมเดลจาก capability และผลทดสอบจริง ไม่ผูกชื่อรุ่นถาวร: งานทั่วไปใช้ tier กลาง; งานกำกวม/เสี่ยงสูงใช้ tier สูง; local ใช้เฉพาะงานใน whitelist ผ่าน guard ตาม RULE 18/22/23 ชื่อรุ่นในนโยบายเก่าอาจไม่ตรงกับ runtime ปัจจุบัน ต้องตรวจ endpoint และ availability ก่อนทุก batch

เริ่ม calibration 10 เรื่องที่ครอบคลุมทุกความเสี่ยง ให้ผู้ตรวจอิสระตรวจทั้งชุด เกณฑ์รับ: ไม่มี critical error, หลักฐานทุกข้อย้อนกลับได้, จับข้อยกเว้นครบ, เมื่อไม่พบหลักฐานต้อง HOLD หลังจากนั้น batch 5 เรื่องหรือ 20 ข้ออ้างต่อรอบ (ค่าเริ่มต้นที่ปรับได้) เก็บ actual tokens, latency และ defect ต่อเรื่อง แล้วปรับ tier ตาม defect ไม่ลดมาตรฐานเพราะใกล้ quota

เมื่อเกิด 429 ให้ checkpoint งานที่ผ่านครบแล้ว เคารพ Retry-After ใช้ bounded exponential backoff และไม่ retry เอกสารที่จบแล้ว กำหนด budget ต่อ batch ทั้ง input/output และเวลา เผื่อ quota ที่ผู้ใช้ต้องใช้ทำงานอื่น ไม่มีการรัน background หรือกำหนดตารางในรอบนี้

คิว `review-queue.json` เก็บ input hash และ citation candidates เพื่อค้นแหล่งเดียวใช้หลายบทความได้ แต่ผล semantic review ยังคงต่อข้ออ้าง/บริบท การ cache ต้องรวม hash ตัวบททางการ, effective date, as-of date, prompt, model version, reviewer และ decision ส่วน shared summary หรือฉบับแปลต้องตรวจแยก ไม่ส่งทั้งคลังเข้าบริบททุกครั้ง

## เชื่อมหน้า /knowledge โดยไม่กระทบส่วนอื่น

1. ยืนยัน revision ของ LAS production และตรวจ `/knowledge` + `/hub/...` หลังเข้าสู่ระบบ ว่าฉบับใดเป็น authoritative ต่อ content ID
2. ย้ายข้อมูลรายการ Popular/Stats แบบ hard-coded ไปอ่าน manifest ที่มี schema ใช้ component/card และ CSS เดิมของหน้า Knowledge เก็บ feature flag ปิดเป็นค่าเริ่มต้น
3. เพิ่ม Tag Card จุดเข้า “เส้นทางการเรียน” เฉพาะหน้า Knowledge ลิงก์ไปหน้ารายการใหม่ ไม่แก้ Landing, Link, Dashboard navigation หรือส่วนกลางอื่นโดยอัตโนมัติ
4. เสิร์ฟ manifest ผ่านเส้นทางที่ใช้ session เดิม ไม่เปิด private Brain 2, source PDFs ภายใน, audit logs หรือฐานข้อมูลออกสาธารณะ ตรวจ allowlist ก่อนแปลง URL เป็น `/hub` ห้าม remap ลิงก์ external ทุกโดเมน
5. ผู้สอนตรวจต้นแบบและ scope diff ก่อนอนุมัติ merge/deploy จากนั้นเปิด feature flag เฉพาะ release ที่ผ่าน gate และมีแผนปิดกลับได้

ต้นแบบนี้อยู่แยกใน `docs/knowledge-teaching/` ไม่โหลดโดย production page เดิม และไม่แก้โค้ด LAS checkout ที่มีงานค้าง เมื่อเปิดใช้จริงต้องเพิ่ม contract test ใน repo LAS โดยใช้ baseline live ณ เวลานั้น ไม่ใช้ checkout เก่าทับ runtime

## เกณฑ์ตรวจรับและลำดับส่งมอบ

- ทะเบียน: ทุกไฟล์มีผล include/exclude และเหตุผล ไม่มี duplicate URL; redirect ไม่เพิ่มจำนวนเรื่อง; article/resource แยกกัน
- Discovery: ทุก approved content ID ปรากฏในการค้นอย่างน้อยหนึ่งช่องทาง ยอดบนการ์ดคำนวณจาก manifest; 29 เรื่องที่ไม่เชื่อมจาก Hub เดิมต้องได้รับการตัดสินใน release ใหม่
- Identity: เคลียร์ 44 override routes ทีละเส้นทาง; ยืนยันว่าคลิกการ์ดแล้วหัวเรื่องและ hash ตรงกับฉบับที่ตรวจ
- Pedagogy: prerequisite ไม่มีวงวน; ทุก lesson ID มีจริง; ผู้สอนรับรองลำดับและแบบฝึก
- Legal: ผ่าน gate เดิมทุกตัว เพิ่ม source/semantic evidence; ไม่มี critical HOLD ในบทที่ติด teaching_ready
- UI: keyboard, mobile, empty state, filter combination, link target, auth/401; ตรวจ Landing/Link/shared assets ไม่เปลี่ยน
- Delivery: PR สำหรับ review, Second Brain เป็น draft พร้อมที่มา, production ต้องอนุมัติแยก และเปิดดูของจริงหลัง deploy

ลำดับถัดไป: ตรวจรับต้นแบบ → reconcile authenticated content → calibration 10 เรื่อง → ตรวจและปรับบทเรียนเป็นชุด → integrate feature flag → ทดสอบและอนุมัติ deploy ไม่มีการอ้างว่าบทเรียนทุกเรื่องพร้อมสอนแล้วในรอบนี้
